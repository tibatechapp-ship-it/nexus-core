### 11.3 F4 — why the RAM budget was re-scoped, not "fixed"

Measured floor of the live process (same box, same interpreter; RSS via
`resource.getrusage` / `VmRSS`):

| Stage | RSS |
|-------|----:|
| bare `python3` | 12 MB |
| + FastAPI / starlette / pydantic (import `nexus_agent`, no LLM call) | **62 MB** |
| + first **live** LLM call — openai SDK + httpx + aiohttp + opentelemetry + truststore, imported lazily on first use | **94 MB** |
| second instance (`:8099`), offline warm, never calls the LLM | 62–70 MB |
| second instance after 1 live debate | 104–124 MB, then **plateaus** (footprint, not a leak) |

Rejected fixes — each measured, not assumed:

- `MALLOC_ARENA_MAX=2` → **94 MB, no change** (not glibc-arena fragmentation).
- `gc.collect()` + `malloc_trim(0)` → `malloc_trim` does **not exist** in
  Android's libc (`undefined symbol: malloc_trim`).
- Reusable `ThreadPoolExecutor` instead of a per-call `threading.Thread` in
  `Council._live_generate` → **no benefit**: 7 throwaway threads added 0 MB
  (94 MB vs 94 MB), so thread stacks are not the cost. **Not applied** — it
  would have touched the Council core for zero gain.

Re-scoped budget: **≤ 96 MB** for the offline/deterministic build,
**≤ 128 MB** for the live-provider build. Going below 100 MB live would mean
replacing the provider SDK (~32 MB) with a stdlib transport — a change to the
protected `src/novamind/core/llm_router.py`, out of scope here. Logged as a
v1.14 candidate improvement, **not** a defect.
